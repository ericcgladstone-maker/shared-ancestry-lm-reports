# GPT Review of Verification Run (2026-10-30)

# Decision and scope

Do not start the full run under the currently verified configuration. Proceed after a narrow correction and verification pass, not a redesign. The principal obstacle is a validation rule that failed 109 Haiku trials. The secondary obstacle is that the cost projection assumes batch reader calls, prompt-cache savings, and three-message reader lengths that the verification run did not actually exercise. The current run.py does not execute any readers in its “full” phase and the current readers.py defines only Study 1 classification tasks. This is a distinction between launching producer generation and completing the specified full run, not a reason to change the scientific design.

The verification demonstrates useful engineering progress. Seventy blocks were attempted across ten reserved worlds and three producers. A graph audit found no problems in 621 realized condition graphs. The report documents expected co-location counts, 180 deterministic source-line stripping operations, low missing-attribution rates for the primary producer, and 150 count-neutral synthesis preflight judgments under the corrected judge. These findings support proceeding after the specific repairs below, but several checks establish a narrower property than the report or brief might imply.

Evidence: the verification brief, report.md and report.json, both preflight\_judgments logs, matcher\_spot\_check.json, build/run.py, residue/matcher.py, residue/readers.py, the generation/store/adapter/audit implementations, and the v8 design principles and build specification. The report comes from code snapshot 354d32f9eccd. Later source files or account-top-up changes must not be mistaken for checks that passed under that earlier snapshot.

# 1\. Finding 1: Haiku truncation

Disposition: CORRECT BUG FIX, WITH A FOLLOW-UP VERIFICATION REQUIRED.

The first cap used approximately 4/3 output tokens per word for every producer. The run recorded 425 truncated Haiku outputs among 510, while the actual Haiku realization was closer to two output tokens per word. These cap hits are request-budget artifacts, not a difference in Haiku's underlying propensity to terminate a report. Choosing a producer-specific tokens-per-word conversion for the \*same target word count\* corrects an adapter error and is permitted by the build specification's requirement to use actual provider-specific token budgets. Keeping the superseded records is appropriate.

This does not change structural labels or graph ancestry. It does change which realized reports are observable rather than truncated and which contain their last-line Sources field. Therefore earlier Haiku missing-source and invalid-output rates are not interpretable as ordinary producer behavior. A final cap test must show that neither the Sources line nor normal report endings are cut off by generation limits. The current code uses approximately two tokens per word for Haiku and 4/3 for Gemini and Luna. For the final length-window change in Finding 4, use the new cap specified below consistently and record finish/stop reasons as well as lengths.

# 2\. Finding 2: Matcher corrections

Disposition: CORRECT ENGINEERING CHANGES, NOT MATCHER VALIDATION.

Allowing a sentence to map to several propositions fixes an obvious false-omission mechanism. Moving the similarity threshold above observed unrelated-sentence similarities is a reasonable repair for the selected nomic-embed-text encoder. Normalizing “fourteen” and 14, thousands separators, and spelled clock times removes known false alterations. These changes are within the build specification's explicitly allowed dozen-message engineering inspection. They do not change the generated text, graphs, or text-only predictor inputs. They can change \*anchored\* proposition preservation, conflict-resolution, and inherited-deviation estimates, so the old and new matcher outputs are not interchangeable.

The default code threshold now reads 0.86, not 0.75. A dozen inspected messages do not establish its precision or recall, and the report correctly reserves proper human coding until after generation. Its 13/20 cross-observer disagreement statistic is a matcher-dependent diagnostic, not validated evidence of 13 genuine differing conflict resolutions. The acknowledged sequence reversal problem is substantive: “A before B” and “B before A” share vocabulary and embedding neighborhood while asserting opposite events. Keep the generated messages. Before reporting anchored inference, add an order-sensitive rule or a validated adjudication step for those disputes, and test it against labeled examples. It is not a reason to hold up text generation so long as the matcher has no role in accepting or excluding a generated call.

There is another matcher limitation worth specifying at that later stage. The current number test can mark a partly altered multi-number proposition as preserved if any value overlaps. The null/deviation calculation also counts shared “neither” conflict resolution as a deviation. Both can inflate or deflate shared inherited-deviation scores. Those are analysis-instrument issues and are not current producer-generation blockers.

# 3\. Finding 3: Corrected single-input synthesis preflight

Disposition: RETAIN F1 ON THE REVISED JUDGING RULE, BUT CHECK ITS ACTUAL INPUT TYPE.

The first judge marked 9 of 50 one-input outputs, exceeding the 5% decision threshold, which would have removed F1. Comparison with the stored judgments shows that most positive flags across input counts quote the mandatory Sources line, which uses names such as “Incident Report” and “Desk Log,” rather than the synthesis report referring to its \*prompt inputs\*. The remaining flags about “accounts differ” are descriptions of an in-world conflict and can be inherited from a parent message. Judging the report body while showing the actual parent message and distinguishing in-world source attribution from reference to the supplied documents repairs a measurement defect. The second judge recorded 0/50 for each of the one-, two-, and three-input cases. Keeping both logs and describing the changed rule is required for transparent interpretation.

The decision to keep F1 is consistent with the \*intended\* principle 1 failure definition. It changes a design decision relative to what the defective initial judge would have triggered, not the graph structure or data-generating rule within retained conditions. The evaluator's definition was corrected after inspecting its false positives, so do not describe the two judge versions as independent corroborating passes.

One qualification: run.py builds the k=1 preflight samples by selecting from three original observations AND three one-step rewrites in the SI-same graph. F1 instead synthesizes one observation. The current zero-flags result shows that the generic synthesis instruction often works on one input, but does not test 50 observations drawn from F1's exact input role. The cheapest confirmation is to examine the already generated F1 cases and supply the remaining F1-like one-input calls needed to obtain 50 matched tests, using the existing synthesis pool and judge v2. Do not decide F1 on the first judge's mislabeled Sources line.

# 4\. Finding 4: Haiku length, decision and exact rule

Disposition: ACCEPT CLAUDE'S WIDER WINDOW, WITH ONE CONSISTENCY REFINEMENT.

The published 0.5–1.5 target rule produces a systematic selection mechanism: 155 of 280 Haiku observation attempts failed, and 109 complete trials failed after retries. An analyst would then see disproportionately the short, atypical Haiku completions rather than its ordinary reports. The study's genre targets remain 220 words for an incident report and 150 for a news brief. A wider 0.5–2.0 acceptance window applied to every producer is preferable to dropping Haiku from cross-producer comparisons or imposing a producer-specific validity rule. The resulting differences in realized report length belong to the measured producer environment and should be reported, not attributed exclusively to model family.

Exact implementation rule: valid\_length \= (0.5 \* target\_words \<= number\_of\_whitespace\_delimited\_words\_in\_report\_body \<= 2.0 \* target\_words), inclusive. The body excludes ONLY the final delimited Sources line, if present. Do not use the field's presence, validity, or contents as acceptance criteria. The same body-counting rule applies to neutral and generative concealment outputs and to all three producers and both genres. This body-only refinement avoids making the number of source names or intentional source suppression determine whether a report is retried. Keep the existing emptiness and narrow meta-commentary checks.

Exact cap: max\_output\_tokens(producer, genre) \= ceil(2.2 \* target\_words(genre) \* measured\_output\_tokens\_per\_word(producer)), with enough margin to accommodate the Sources field and natural termination. Keep a versioned per-producer conversion table and capture whether a response stopped on an output-token cap. If a source line with unusually long names consumes the margin, increase cap headroom rather than relax the text validator selectively for that function or arm. The cap is a generation safety limit, not a target number of words.

This is a procedural adjustment with an inferential consequence: the accepted distribution of report lengths and retained messages will change, especially for Haiku, and length itself may contribute to across-producer prediction. It does not alter the ancestry labels, the within-producer contrast definitions, or the existing fixed word targets. Run the verification checks again on messages accepted under this rule and recompute provider costs from those actual attempts. Because the requested re-verification is inexpensive relative to the full run, another uniform verification pass is preferable to inferring success from the 109 previously failed trials. Retain superseded attempts separately.

# 5\. Finding 5: Copying on rewrite, decision and exact rule

Disposition: ACCEPT COPYING, DO NOT RETRY FOR IT.

An unchanged rewrite is a legitimate observed outcome when the instruction asks a model to rewrite but the model elects to reproduce the input. It may make a nominal five-step chain resemble a shorter realized editing chain. Rejecting copies would make output selection depend on the very variation the experiment needs to observe and would disproportionately affect Gemini and Haiku. The reported exact-copy rates are approximately 7% for both, versus 0% for Luna. The near-copy classification is more common for Haiku, but it is a heuristic based on vocabulary membership and length, not a measured semantic edit distance.

Exact rule: identical and near-identical valid outputs pass unchanged; never retry because of copying. Record exact byte identity, a declared text-similarity/near-copy measure, nominal rewrite depth, and the number of stages that actually changed the text on each realized chain. Keep the structural label determined by the graph, not by whether a node changed its parent's string. Report effect modification by realized number of non-copy rewrites descriptively and avoid calling it an independently randomized factor.

The choice does not change the intended intervention or the structural labels. It conditions interpretation of depth and ancestry recovery on the model's actual text-editing behavior, which is part of the production mechanism.

# 6\. Passed checks whose actual scope is narrower than claimed

Lineage and prompt content: the audit's zero problems over 621 \*realized\* conditions establishes agreement between realized node functions/parent references and its fixtures for the conditions that returned usable nodes. It does not establish that every planned condition completed, as 109 Haiku trials failed, nor that prompts contain “exactly” parent texts in a byte-level sense. In audit.py, the positive check is substring membership of each parent's text, and the negative check searches for other known node-output strings. An extra instruction or an unseen non-parent string would not necessarily be detected. Cheap independent check: reconstruct each expected request from the versioned renderer and its exact parent-text list, compare request hashes, and separately reconcile planned versus realized condition counts by producer and world. The log's key reuse and zero mismatched stored texts are still useful evidence, but should not be called an end-to-end completeness check.

Co-location and allocator invariants: F2 and F3 each show five trials with each conflict pair co-located among the ten primary-producer worlds, as designed. This demonstrates the rotation. It does not independently verify package-union equality, exact disjointness/overlap, or all other producers. The allocator asserting its own constraints is not an independent oracle. A compact fixture-based package check on the realized records, including non-primary producers and diverse-package conditions, closes this narrow gap.

Attribution field: the report shows high Sources-line compliance and about 94–99% source-name agreement in the neutral primary/OpenAI outputs. This is not a universal pass. The report's source checker accepts substring matches to an in-world source name, not exact equality of canonical names, and it does not establish that a claimed source actually supports the asserted surviving proposition. Haiku figures are calculated among returned usable outputs after disproportionate length-based rejection, so its 100% is selected, not a raw compliance rate. The primary producer's concealment \*observation\* calls correctly retain Sources because neutral source observations are reused. It is only concealment rewrites that are expected to omit the line. Retain presence, exact-name validity, and factual-source consistency as distinct outcomes.

Stripping: 180 of 180 neutral message terminals have a Sources line, and the processing function removes it. However the “deletion exact” statistic is checked using the same strip\_sources function that produced the stripped output, so it is largely a self-consistency check rather than an independently specified expected-byte comparison. The 12/12 matcher invariance check is similarly expected because the matcher calls body(text), which strips the Sources field before extracting features. Neither statistic validates the proposition matcher. A one-page independent byte-diff check for all 180, with a known expected newline rule, is the cheapest stronger test.

Matcher: twelve messages plus nominal state counts (137 preserved, 80 omitted, 16 altered, 7 qualified, 61 unsupported sentences) constitute an engineering inspection, not evidence of sensitivity or specificity. Sequence reversals and overlapping number sets can still corrupt classifications. The 13/20 different conflict-resolution result for independent Gemini observers is provisional until the post-run human annotation. Do not use it as proof that enough independent deviations exist to ensure prediction accuracy.

Single-input preflight: version 2 is a defensible correction to the false-positive flag criterion, but the actual test set mixes original observations with rewritten descendants from SI-same. It does not show 50 F1-like single-observation synthesis inputs. The no-problem result is a valid generic one-input test, not a complete F1-specific test. Confirm the actual F1 input condition separately as specified in Section 3\.

Reader format and prediction: the verification ran single-message Study 1 tasks “depth,” “independence,” “inert,” and “partition,” a total of 100 classification items per reader. All valid first-pass replies demonstrate a functioning single-message reader parser. They do not test the three-message Study 2 set prompt, its five-partition probabilities, randomized presentation order, coherent pair marginals, or its output sizes. The report explicitly says set-reader prompts were not run. There is also no reader invocation in run.py's full-phase branch, and readers.py currently defines only the four Study 1 tasks. A producer run could finish without any of the advertised full-run reader data. Implement and smoke-test the existing Study 2 reader contract and actual full-run reader stage before describing the entire study as executable. This is an implementation completion task, not a new reader design.

Predicted cost: the count of 32,940 producer calls follows from the mock full plan, with shared keys counted once. The dollar projection is not a verified authorization to spend. Verification included costly invalid Haiku retries under the old length rule. Reader totals apply a 2.8x multiplier to untested set-reader payloads and assume batch API pricing and effective prompt caching. The current single-message reader code calls synchronous adapters through a thread pool, not the batch API. A named future batch implementation and cache behavior are not yet tested by those successful synchronous calls.

# 7\. Full-run decision and required changes

Verdict: NOT YET CLEARED AS THE COMPLETE FULL RUN. Findings 4 and 5 can be decided as above, but two further implementation checks affect completion and the spending authority. The producer-only phase can be released as a separate step once the Haiku validation rule is corrected, a brief re-verification succeeds, and the producer-only cost cap is reconciled. It should not silently be treated as proof that the complete producer-plus-reader study is executable.

Required before spending on approximately 32,940 producer calls:

First, apply the common body-length acceptance rule and token cap from Section 4 in the actual call store and provider adapters. Re-run the reserved-world verification under the final version, examine failures/retries by producer, function, arm, and condition, and recompute costs from actual successful completions. Do not include the old length-induced Haiku failures in the final design's estimated failure rate. Run the F1-specific preflight and the independent request/package checks described above as part of that verification. Preserve previous logs and code snapshot.

Second, reconcile the provider ledger against current credit. The verification report's old OpenAI ledger lists a \$17.61 cap, \$6.94 spent, and \$10.67 remaining. The brief says a later \$5 top-up yielded approximately \$16 remaining. The later adapters.py source lists a \$22.94 cap, which is consistent with roughly \$16 remaining at \$6.94 spent. Those are versioned snapshots, not one contemporaneous measurement. Read the actual account and ledger immediately before launch and enforce the refreshed hard caps on the dispatcher.

Third, verify actual reader execution and price rather than the projection's assumed discounts. The verification report calculates approximately \$17.05 Anthropic and \$8.80 OpenAI for producers at standard rates plus readers at batch and assumed cache discounts. By contrast, its own un-discounted reader figures are about \$96.51 for Sonnet and \$25.18 for Terra. At batch pricing WITHOUT cache hits, the combined provider totals would be about \$53.87 Anthropic and \$14.67 OpenAI. The former exceeds the approximately \$35 remaining Anthropic credit even before allowance for changes in length or set prompts. The latter is below the later \$16 OpenAI balance but has little margin. This establishes that the Anthropic projection relies materially on caching, not just on “batch.”

The least expensive decisive test is to construct genuine Study 2 reader prompts with 18 labeled sets, submit a small representative batch on both reader APIs, observe billed input/output tokens and cache-read usage, and use those measurements to recompute both reader budgets with a no-cache or low-cache scenario. The projected three-message input multiplier should then be replaced with actual prompt token counts. Confirm the chosen reader batch endpoint is implemented and that it returns valid three-class/set and pairwise probabilities under the intended five-partition contract. If the conservative projected costs exceed a provider's verified available credit, add credit or defer the reader stage with an explicit account reserve. Do not launch a purported full run on an unverified cache-read assumption. A hard provider stop protects the account but can leave entire conditions or readers absent in a nonrandom pattern.

Fourth, ensure that the full pipeline actually runs or schedules the reader stage and collects all planned reader inputs. The current run.py main path executes verification readers only inside verification\_report. In its full branch it runs producer blocks, then exits without any reader dispatch. This is the most concrete missing build component after length validation and cost checks. It is permissible to run producer generation and readers as separately checkpointed stages, but then name them and verify that the second stage will consume the correct primary-producer first-replicate messages and sets. It must not introduce a world or label leakage when drawing training-world exemplars.

The sequence-sensitive matcher and final human-coding validation are necessary for credible anchored mechanism results, not for generating producer texts. They can remain downstream as the build specification explicitly states. Do not let provisional matcher classifications gate or filter generated trials. Likewise, copying must remain accepted and logged. There is no reason here to alter the graphs, history labels, prompt pools, sampling design, or the scope of the study.
